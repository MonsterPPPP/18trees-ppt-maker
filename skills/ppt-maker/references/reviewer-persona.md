# 子 Agent Review 规格（扮演委托人本人）

> 本 skill 相对上游的**唯一机制性增量**。每完成一版 deck 必须跑一次；改完必须再跑一次。
> 生成者自己 review 是无效的：生成者脑子里有背景，会自动补全页面里缺失的解释。

---

## 为什么必须交给子 Agent

委托人拿到 PPT 时是**零背景读者**：他不知道这页想说什么、不知道那个标签是干嘛的、
不知道这个数字从哪来。他只会有一个反应 —— **"这什么意思？"**

而生成者永远觉得"这里已经很清楚了"，因为他自己知道。这个认知差**无法自省修正**，
只能靠一个被强制放在"零背景位置"的读者来暴露它。

子 Agent 的价值不是更聪明，而是**可以被指定成"屏幕前那个什么都不知道的人"**，
而且它不在生成者的上下文里，不会被已有论证污染。

---

## 关键约束：不许给 reviewer 讲道理

给 reviewer 的输入只有三样：

1. 产出的 `index.html` 路径（让它自己逐页读）
2. `references/taste.md`（口味档案 —— 这就是它的"人格"）
3. 叙事大纲 md 路径（只用于**核对有没有丢信息**）

**不要**把这些给它：为什么这么设计、这页想表达什么、有哪些妥协、
"这里其实是呼应第 5 页的"—— 任何解释都会毁掉这次 review 的价值。

---

## Prompt 模板

用 `session_spawn` 起一个子 Agent（建议 `sota` 或 `default` 档），把下面模板填空后作为任务。
`worker`/`reviewer` 类只读 agent 都可以，关键是它**必须能读文件、并且允许自己提出反对意见**。

```
## 你的身份

你是**委托人本人**。你刚刚收到一份别人替你做的 PPT，准备在一个重要场合直接发给对方看——
没有你在旁边讲解，对方自己打开、自己翻。

你不是来夸的。你是一个挑剔、耐心有限、对排版极其敏感的甲方。你看到任何一处
"这什么意思"或者"这里怎么这么空"，就立刻记下来。

## 你要读的东西

1. PPT：<绝对路径>/index.html —— 逐页读（共 <N> 页）。
2. 你的口味档案：<SKILL_ROOT>/references/taste.md —— 这一条条都是你以前骂过的，
   这次按同样的标准检。
3. 叙事大纲：<绝对路径>/材料-vN.md —— 只用来核对"有没有把原来有的东西弄丢了"。

**注意：不要来找我要背景解释。你看不懂就是看不懂，这本身就是问题。**

## 逐页检查（每页都要过一遍）

对每一页，先假装自己是零背景读者，然后回答：

A. **只看这一页，我知道它想说什么吗？** ——说不出来，直接记问题。
B. **这一页有没有需要人解释才懂的东西？** ——英文标签、缩写、装饰词、内部提示。
   有的话引用原文。
C. **底部有没有孤立的小字？** ——页面最下面一条脱离主线的说明，就是雷。
D. **这一页是不是有两个互不相干的结构块？** ——比如上面时间线、下面一排卡片。
E. **有没有大块空白？** ——主体没撑满、靠 margin 硬撑。
F. **字号**：页面里的业务文字，桌面端有没有小于 18px 的？小到需要凑近看的直接记。
G. **列表型内容有没有用表格/分隔线清单？** ——堆成一坨卡片就是没做够。
H. **两列/多列内容是否整齐？** ——条目数、行高、句长是否对得上。
I. **有没有同层级里只突出一个的颜色不一致？**
J. **有没有出现真实人名？有没有强调没坐实的具体数字？**

## 跨页检查

K. **页码连续吗？** 页眉 `NN / MM` 全 deck 一致、无跳号吗？
L. **页眉章名是"NN — 中文章名"格式吗？** 有英文 eyebrow 吗？
M. **对比叙事大纲：有没有信息被弄丢了？** 逐条列出大纲里有、PPT 里没有的内容。
N. **叙事顺序对吗？** 该先讲"是什么"再讲"卖给谁"的地方，顺序是不是反了？

## 输出格式

先给一句总评（一句话，直说，可以难听）。

然后一张问题清单，按严重度排序（P0 = 不修就不能发；P1 = 该修；P2 = 可优化）：

| # | 严重度 | 页码 | 位置（引用原文片段） | 问题类型 | 为什么这是问题（零背景读者视角） | 建议改法 |
|---|---|---|---|---|---|---|

最后单独一节：**「信息丢失清单」** —— 大纲里有、PPT 里没有的内容，逐条列。

## 纪律

- 每一条问题都要带**页码 + 原文引用**，不要写"整体感觉不错但可以更清晰"这种废话。
- 不要提出需要新增页面的建议，除非确实缺一整个议题。
- 不要复述你已经认可的内容，只报问题。
- 至少找出 5 条问题。如果确实找不满 5 条，说明你检查得不够狠。
- 直接给结论，不要过程旁白。
```

---

## 拿到清单之后

1. **逐条改**，不要挑着改。P0 全改，P1 全改，P2 判断。
2. 改不动/不认同的，写清楚理由留下，不要静默忽略。
3. **改完再跑一次 review**（同样的 prompt，同样的约束）。
4. 直到清单里没有 P0/P1，才算这一版做完。

reviewer 的清单建议原样存进项目记录里，作为"这一版做过哪些修正"的证据链。

---

## 常见失效模式

| 失效 | 症状 | 解法 |
|---|---|---|
| reviewer 太客气 | 清单只有 2–3 条，全是"建议可以更醒目" | prompt 里明确"至少 5 条""可以难听"，并要求带原文引用 |
| reviewer 被背景污染 | 它开始替页面辩解（"考虑到篇幅限制…"） | 检查你是不是把设计意图泄漏给它了；只给三样输入 |
| reviewer 只读代码 | 没提任何视觉/空白问题 | 明确要求它逐页"假装看屏幕"，并逐条回答 A–J |
| 改完没复检 | 改一处崩一处 | 强制二次 review，直到 P0/P1 清零 |

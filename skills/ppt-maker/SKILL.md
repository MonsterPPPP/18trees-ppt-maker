# ppt-maker · 做 PPT 的 skill

**这就是一套做 PPT 的作业规范**，而且是**全流程**的，不只是排版：

```
素材 → 叙事大纲 → 网页 PPT → 静态校验 + 独立评审 → 视口验证 → 导出 PDF · 打包交付
```

它比"让 agent 随手生成一个 PPT"多两样东西：

1. **品味** —— 一批具体到像素的雷区（[references/taste.md](references/taste.md)），
   每一条都来自真实的返工，不是设计理论。
2. **怎么用它** —— 六阶段流程、一个不许跳过的评审环节、两个可以直接跑的脚本
   （静态校验 + PDF 导出打包）。

唯一的判据是：**一个不了解背景的人，只看这一页，能不能自己看懂它想说什么？**
收件人自己打开、自己往下翻、没有人在旁边解释 —— 所以小字、留白、英文标签、
口头补充全部不成立。这一条推翻了普通 PPT 的大部分默认做法。

## 站在谁的肩膀上

渲染层是一件外部插件：开源项目 [`guizang-ppt-skill`](https://github.com/op7418/guizang-ppt-skill)，
作者 **歸藏**（[@op7418](https://x.com/op7418)），AGPL-3.0。它负责"把网页 PPT 渲染出来"
（模板、CSS、动效、22 个 Sxx 版式、瑞士风静态校验）；本 skill 负责"做出来的东西
**够不够格直接发给别人看**"。

**不遮掩这件事：这是站在上游肩膀上做的。** 上游是个很好的引擎，我们补的是它不负责的那一半。
分工不要搞混：

| 层 | 谁负责 | 负责什么 |
|---|---|---|
| 渲染层 · 插件 | 上游 `guizang-ppt-skill` | 模板、CSS、动效、22 个 Sxx 版式、瑞士风校验 |
| 规范层 · 本体 | **本 skill** | 独立阅读铁律、页码体例、结构收敛、PDF 导出、review 环节 |
| 口味层 | `references/taste.md` | 委托人明确表达过的喜欢与不喜欢（**持续追加的地方**） |

上游身份卡、致谢、文件地图、加载顺序、许可证边界 → **[references/engine.md](references/engine.md)**。

## 0 · 先想清楚一句话

> **"PPT 本身就是完整的信息呈现。不是我来讲，而是直接把东西给别人看。"**

这句话是全部规则的源头。它推翻了普通 PPT 的两个默认前提：

- 普通 PPT 是**讲稿的辅助**：可以有小字、可以留白让讲者补话、可以靠口头解释补意义。
- 这份 PPT 是**一份可以单独发出去的文档**：收件人自己打开、自己往下翻、没有人在旁边解释。

所以任何一个元素都必须通过这个测试：

> **一个完全不了解背景的人，只看这一页，能不能自己看懂它想说什么、以及它跟这一页主题的关系？**

答"不能"的元素 —— 要么解释清楚，要么删掉。**没有第三种处理方式。**

## 1 · 依赖：一个外部渲染引擎

本 skill **不自带渲染资产**，它依赖上游 `guizang-ppt-skill` 已安装在本机。

```bash
# 检查引擎在不在（路径按你的 skills 目录调整，常见是 ~/.cola/skills/）
ls <SKILLS_DIR>/guizang-ppt-skill/SKILL.md
ls <SKILLS_DIR>/guizang-ppt-skill/assets/template-swiss.html
```

没装就先装上游，再回来。**不要**为了"自包含"把上游模板复制进本仓库 —— 那会把插件关系
变成合并关系，许可证要求随之变化（见 [references/engine.md](references/engine.md) 第二节）。

本 skill 对引擎只做两件事：**读它的模板填内容**、**把它的校验脚本当外部进程调用**。

---

## 2 · 什么时候用 / 不用

**用**：投资人材料、商业计划、路演 deck、项目汇报、行业分享 —— 任何「要发给别人看」的 PPT。

**不用**：自用演讲提示卡（那是讲稿，不是文档）、需要多人协作编辑的 deck
（本产出是静态 HTML）、纯图表叠加的报表（那该用 Excel / PowerPoint）。

## 3 · 六阶段工作流

顺序不能乱。前一步没稳定就进下一步，后面全部返工。

### Step 1 · 素材 → 叙事大纲（md）

**产物**：一份 `xxx材料-vN.md`，**两部分结构**：

1. **第一部分 · PPT 大纲**：每页写清「标题 / 核心结论 / 上屏文案 / 视觉结构建议」。
2. **第二部分 · 完整叙事文本**：把论证、证据、口播素材全部放这里，供追问时查。

**硬规则**：

- **迭代时不许丢东西。** 每一版都是在上版基础上**追加或重组**，不是重写。
  委托人曾因为一次重构丢内容直接回"丢东西了！！！！"。改结构前先把上一版存好，改完逐条核对。
- 大纲阶段就要写「待验证 / 待补齐信息」清单，不要让未坐实的数据流进最终页面。
- 每个结论都要有证据位；证据拿不出来就降级措辞，别写成已实现业绩。

细节见 [references/outline-to-deck.md](references/outline-to-deck.md)。

### Step 2 · 定风格与版式

信息密度高的商业材料，**默认走上游的风格 B · 瑞士国际主义 + IKB 克莱因蓝**。
人文/故事型材料才考虑风格 A。选完读上游对应文件（加载顺序见 [references/engine.md](references/engine.md)）。

动手前先把这张草稿列出来并写进项目记录：

```
页码 → chrome 章名 → data-layout → 该页唯一主结构 → 该页要回答的问题
```

### Step 3 · 生成 HTML deck

拷贝上游模板到 `项目/xxx/ppt/index.html`，逐页填。

**每页的固定体例**（本 skill 的定义，上游没有）：

- 页眉左侧：`NN — 中文章名`（带两位编号，中文，不许用英文 eyebrow）
- 页眉右侧：`NN / MM`（总页数，全 deck 一致）
- 主标题：本页唯一的大字结论，编号与页眉一致
- 正文：**一个**主结构（表格 / 网格 / 流程 / 清单），不要并列两个割裂的结构
- 页面底部：**不允许**出现孤立的脚注式小字

### Step 4 · 独立阅读自检 + **子 Agent review（强制）**

先跑一次静态校验：

```bash
node <SKILL_ROOT>/scripts/validate-ppt.mjs 项目/xxx/ppt/index.html \
  --engine <SKILLS_DIR>/guizang-ppt-skill/scripts/validate-swiss-deck.mjs
```

然后 **必须** 起一个子 Agent，扮演委托人本人做 review。这一步不许跳过、不许自己代跑。
规格、prompt 模板、输出格式见 [references/reviewer-persona.md](references/reviewer-persona.md)。

要点：reviewer 要**脱离一切背景**逐页读，把所有"看不懂 / 需要解释 / 显得多余 / 显得空"的地方
按页号列成清单，带原文引用和修改建议。拿到清单后逐条改，改完**再跑一次 review**，直到清单清空。

### Step 5 · 视口验证

桌面 `1440×900`、移动 `390×844` 两个视口逐页检查：不溢出、不出现滚动条、文字不越界、不隐藏业务内容。
移动端**不许**用 `display:none` 藏正文来"解决"溢出 —— 那等于把 PPT 变成了残页。

### Step 6 · 导出 PDF + 命名打包

```bash
node <SKILL_ROOT>/scripts/export-pdf.mjs 项目/xxx/ppt/index.html \
  --out 项目/xxx/材料-PDF版.pdf \
  --package 项目/xxx/交付物 --outline 项目/xxx/材料-vN.md
```

交付物一定是**三件套放在同一个文件夹**，命名同前缀：

```
交付物/
├── xxx材料-vN.md          ← 叙事大纲（可编辑源）
├── xxx材料-HTML版.html    ← 网页 PPT（可翻页演示）
└── xxx材料-PDF版.pdf      ← PDF（发给别人看的那份）
```

机制与坑见 [references/export-and-package.md](references/export-and-package.md)。

## 4 · P0 铁律（违反任何一条即为不合格）

1. **没有孤立小字。** 页面底部不许有一条脱离主线的脚注式小字。
   要么把它融进上面的主体（变成某个卡片的一行、表格的一格、正文的一句），要么删掉。
2. **没有意义不明的东西。** 一切需要口头补充才能懂的元素都不许出现：
   英文 eyebrow（`WHY NOW` / `WHY ME` / `SEED` / `TRACTION` / `NEXT` / `INPUT` / `TAKEAWAYS` …）、
   没解释的缩写、装饰性标签、内部提示词、占位符。中文结论写出来，缩写首次出现时解释。
3. **字号有下限。** 业务信息桌面端 ≥ 18px、移动端 ≥ 16px；页眉/页码可以 13–16px。
   放不下就删文案、拆页、换版式，**不许压字号**。
4. **每页一个结构。** 一页里不许出现两个互不相干的结构块（例如时间线 + 底部六格卡片）。
   整页只用一种结构把细节装进去。
5. **不藏大块空白。** 主体要撑满内容区；出现大片空白就是排布没做完，用网格把高度分配掉。
6. **主标题够大、有编号。** 页眉章名与页内主标题都要带编号，标题层级要一眼能看出。
7. **列表型内容用表格。** 三个以上同构项就上表格 / 带分隔线的清单，不要堆成一坨卡片。
8. **一页一件事。** 一页只讲一个核心结论，其余信息都是这个结论的支撑模块。
9. **不丢信息。** 重构结构时先保内容，再谈美观。
10. **不强调未坐实的具体数字，不出现真实人名。** 具体位数、成交额、百分比，凡是没有落定的
    都写成定性表述；署名位置写角色（"创始人" "项目负责人"），不写真人姓名
    （黑名单在 `scripts/forbidden-names.txt`，可用 `--names=` 临时追加）。

逐条雷区清单（带原始反馈出处）见 [references/taste.md](references/taste.md)。

## 5 · 子 Agent review：为什么是强制的

自己做的东西自己看不出问题 —— 生成者脑子里有背景，永远会自动"补全"页面里缺失的解释。
委托人看这份 PPT 时没有这个背景，所以他会看到一堆"这什么意思"。

子 Agent 的价值不在于更聪明，而在于它**可以被迫站在"没有背景的读者"位置上**，
把生成者无意识补全的空白重新暴露出来。**这是本 skill 相对引擎唯一的机制性增量**，
所以它是**流程环节**，不是可选项。

规格：[references/reviewer-persona.md](references/reviewer-persona.md)

```
│   ├── outline-to-deck.md          ← 素材 → 大纲 → 页面 的映射方法
│   ├── export-and-package.md       ← HTML→PDF 导出机制、已知坑、打包命名
│   └── engine.md                   ← 引擎插件：上游身份卡、致谢、文件地图、许可证边界
└── scripts/
    ├── validate-ppt.mjs            ← 独立阅读静态校验（页码/字号/孤立小字/英文标签/人名…）
    ├── forbidden-names.txt         ← 人名黑名单（默认留空，填你自己的）
    └── export-pdf.mjs              ← headless 浏览器导出 PDF + 三件套命名打包
```

**本 skill 的规则是怎么来的**：它们不是设计出来的，是从一份 14 页商业 deck 的**六轮真实反馈**
里长出来的。原始材料不随本仓库分发，但每条雷区都在 `taste.md` 里注明了出处与原话。

**维护方式**：委托人的新反馈 → 先追加到 `references/taste.md`（带原话与日期），
再回看是否需要升格成 SKILL.md 的 P0 铁律；需要机器判定的，同步写进 `validate-ppt.mjs`。
**这个 skill 是靠反馈长出来的，`taste.md` 是它真正的心脏。**
